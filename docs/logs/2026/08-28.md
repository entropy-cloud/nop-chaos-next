### 2026-08-28 (post-closure: extension-demo packaging defect discovered)

While spot-checking the Phase 5 exit criteria against the actual build output of `examples/extension-demo`, three defects surfaced that are **out of scope for plan 43** but block the production contract end-to-end:

- **Defect A — wrong build entry**: `examples/extension-demo/index.html:10` references `/src/standalone/main.tsx`. Because `vite.config.ts` does not declare `build.rollupOptions.input`, Vite picks `index.html` as the implicit entry. The actual extension entry `src/index.ts` (which `export default extension`) is therefore **not included** in the production bundle. `pnpm build` emits `dist/assets/index-qkUISkkI.js` whose body is the standalone React preview, not the extension entry. As a result the `extension.json.entry` value `./assets/index-qkUISkkI.js` resolves to the wrong script — `bootstrapExtensions()` would either fail to import the `extension` object or pull in a React tree that calls `createRoot(...).render(<Xt />)` against the host's `#root`.
- **Defect B — missing static assets from `src/`**: even when forcing `src/index.ts` as the build entry, `dist/` does not emit `harbor-mark.svg`, `harbor.css`, `shell.css`, `component-page.css`. These are referenced via `new URL('./xxx', import.meta.url)` in `src/index.ts:6-10`. Vite inlines only what is reachable from a code-splitting entry. Because `src/index.ts` only assigns the URLs to fields on the `extension` object (logoUrl / markUrl / cssHref / styles[*].href / i18n.baseUrl) and never imports them statically, the bundler treats them as pure string literals and does not emit the assets. The `extension.json.styleAssets` field only contains `index-CEFMpR-c.css` (the bundled Tailwind output) — none of the `src/*.css` references appear there because they are not in `styleAssets` either; they are inside the per-extension field arrays that `extension.json` does not capture.
- **Defect C — `extension.json` only captures the entry chunk and the bundled CSS, not the per-extension field assets**: `extensionManifestPlugin` (`examples/extension-demo/vite.config.ts:12-41`) iterates `bundle` and only adds (a) the entry chunk and (b) `.css` assets emitted by Vite itself. It has no view of `new URL(...)` references inside source files. Therefore `extension.json` is silent about `harbor-mark.svg`, `harbor.css`, `shell.css`, `component-page.css`, and `locales/` (the latter is reachable via `public/locales` so it is copied — that part is OK).

**Net effect**: plan 43 closed correctly for the **host-side** contract (DOM scan recognises `<script data-nop-extension>`), but the **extension-side** delivery is broken end-to-end. The plan as scoped only required Java → front-end compat; the actual extension build is owned by `examples/extension-demo` and was not part of plan 43's scope.

**Successor plan**: see `docs/plans/44-extension-demo-build-pipeline.md` (next plan) for the fix scope: switch the build to library mode with `src/index.ts` as the explicit `rollupOptions.input`, capture the `new URL()` references as additional `styleAssets` (or per-field `assets` block) entries in `extension.json`, and verify against the deployment structure under `META-INF/resources/extensions/{name}/` (复数 `extensions`, 与 base path `/extensions` 对齐).

  - Java `IndexHtmlProvider` (in `nop-entropy-master/nop-frontend-support/nop-web`) adopts a server-side whitelist + direct `<link>` / `<script type="module">` injection model, replacing the older single-file `extensionsPath` template mechanism (commit `ff641f7dee` "feat(web): 重构IndexHtmlProvider支持多扩展加载").
  - Compared with `apps/main/src/extensions/config.ts` (window injection) and `packages/extension-host/src/loadExtensions.ts` (dynamic `import()`):
    - **Server-side whitelist** (`nop.web.index-extension-names`) gives the deploy environment full control over which extensions are loaded; front-end cannot bypass it.
    - **CSS `<link>` in `<head>`** is parsed by the browser before application JS executes, reducing FOUC.
    - **Frontend / backend decoupling**: Java only reads `extension.json`; no knowledge of how each extension's JS bundle wires into the host runtime.
  - Verdict: the Java-side contract is the better default for production deployment. The current nop-chaos-next front-end `window.__NOP_EXTENSIONS__` path is still useful for the prototype / local-alias dev workflow, so both contracts should coexist.
